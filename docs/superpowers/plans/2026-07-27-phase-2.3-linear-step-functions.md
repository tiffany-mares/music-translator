# Phase 2.3 — Linear Step Functions Pipeline — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the pre-chunking Step Functions pipeline `MarkProcessing → RunMLPipeline → RunTranslation → MarkComplete/Failed` (architecture.md §4 reduced to its linear form, §10 item 2.3), triggered manually with a test payload — no API layer.

**Architecture:** Mark* states are direct DynamoDB `updateItem` service integrations (no Lambda, per §4's sketch). `RunMLPipeline` is `sagemaker:createProcessingJob.sync` running the existing `lyralearn-ml:2.2` container on the whole song. `RunTranslation` is a new container-image Lambda that reuses `stages/translate.py` (MarianMT ROMANCE-en, baked into the image — the 2.2 lesson applied from day one) reading `transcript.json` from the job's S3 output and writing the §6.2-shaped `song_lyrics.json` back to S3. Infra follows the repo's established CLI + committed-JSON-template pattern (`infra/aws/` + `scripts/aws/`).

**Tech Stack:** Step Functions (STANDARD), DynamoDB (on-demand), Lambda container image (Python 3.11, torch-cpu + transformers), ECR, AWS CLI, pytest.

## Decisions locked during planning

- **Lyrics land in S3 only** (`songs/{songId}/lyrics/song_lyrics.json`, exact §6.2 doc shape) — user-confirmed. MongoDB Atlas write is Phase 3's business; S3 docs are backfillable.
- **CLI + JSON templates, not Terraform** — consistent with 2.1/2.2. User decision (2026-07-27): Terraform adoption is **committed as Phase 3's first task** — write §7's `orchestration`/`storage`/`ml-processing` modules, import the ~14 CLI-created resources, pick a state backend — and Task 6 records this commitment in `notes/phase2.md` and `CLAUDE.md` so Phase 3 planning inherits it as a hard prerequisite, not a suggestion.
- **No GSIs yet** on `LyraLearnTable` — GSI1/2/3 serve API-layer queries (Phase 3); the pipeline only does keyed `UpdateItem`s. PK/SK only.
- **Quota split:** everything except the two done-when executions needs **no GPU quota**. Bonus: a pre-approval execution exercises `MarkProcessing → RunMLPipeline-fails(ResourceLimitExceeded) → MarkFailed` — real early validation of the catch wiring (Task 5). The execution shows **green** in that case: `MarkFailed` is a normal `End` state; "failure" is recorded in the job item's `status=FAILED`, which is exactly §4's design (the Streams-triggered push in Phase 6 reads that write).

```python
        return {"Body": io.BytesIO(json.dumps(self._transcript, ensure_ascii=False).encode("utf-8"))}

    def put_object(self, **kwargs):
        self.put_calls.append(kwargs)
        return {}
```

```python
"""RunTranslation Lambda (Phase 2.3): transcript.json in S3 -> translated
section 6.2 song_lyrics.json in S3.

Runs as a container-image Lambda with the MarianMT ROMANCE-en model baked
into the image at /opt/model (same weight-baking lesson as Phase 2.2 - no
Hub download at invoke time). Reuses stages/translate.py's translate_lines
verbatim; the model is loaded once per execution environment and reused
across warm invokes.

Lyrics land in S3 only at this phase - the MongoDB Atlas write is the Phase 3
API layer's concern (user decision, 2026-07-27).
"""
import json
import os

import boto3
from transformers import MarianMTModel, MarianTokenizer

from stages.translate import translate_lines

MODEL_DIR = os.environ.get("TRANSLATE_MODEL_DIR", "/opt/model")

_S3 = None
_TRANSLATOR = None


def _s3():
    global _S3
    if _S3 is None:
        _S3 = boto3.client("s3")
    return _S3


def _translator():
    global _TRANSLATOR
    if _TRANSLATOR is None:
        _TRANSLATOR = (
            MarianTokenizer.from_pretrained(MODEL_DIR),
            MarianMTModel.from_pretrained(MODEL_DIR),
        )
    return _TRANSLATOR


def handler(event, context):
    song_id = event["songId"]
    bucket = event["bucket"]
    transcript_key = event["transcriptKey"]

    body = _s3().get_object(Bucket=bucket, Key=transcript_key)["Body"].read()
    transcript = json.loads(body)

    tokenizer, model = _translator()
    lines = translate_lines(transcript["lines"], tokenizer, model)

    doc = {
        "songId": song_id,
        "sourceLanguage": transcript.get("sourceLanguage", "ro"),
        "targetLanguage": "en",
        "lines": lines,
    }
    lyrics_key = f"songs/{song_id}/lyrics/song_lyrics.json"
    _s3().put_object(
        Bucket=bucket,
        Key=lyrics_key,
        Body=json.dumps(doc, ensure_ascii=False).encode("utf-8"),
        ContentType="application/json",
    )
    return {"lyricsKey": lyrics_key, "lineCount": len(lines)}
```

```bash
#!/usr/bin/env bash
# Phase 2.3: start one pipeline execution and watch it to a terminal state.
# Usage: AWS_REGION=... ACCOUNT_ID=... scripts/aws/start_pipeline_execution.sh <songId> <jobId> [execName]
set -euo pipefail
: "${AWS_REGION:?}" "${ACCOUNT_ID:?}"
SONG_ID="${1:?songId}"; JOB_ID="${2:?jobId}"
EXEC_NAME="${3:-${JOB_ID}-$(date +%Y%m%d-%H%M%S)}"   # becomes part of the job name; keep short
SM_ARN="arn:aws:states:$AWS_REGION:$ACCOUNT_ID:stateMachine:lyralearn-pipeline"

EXEC_ARN=$(aws stepfunctions start-execution --state-machine-arn "$SM_ARN" --name "$EXEC_NAME" \
  --input "{\"songId\":\"$SONG_ID\",\"jobId\":\"$JOB_ID\"}" \
  --region "$AWS_REGION" --query executionArn --output text)
echo "started: $EXEC_ARN"

while true; do
  STATUS=$(aws stepfunctions describe-execution --execution-arn "$EXEC_ARN" \
    --region "$AWS_REGION" --query status --output text)
  echo "$(date +%T) $STATUS"
  [ "$STATUS" != "RUNNING" ] && break
  sleep 30
done

echo "--- job item ---"
aws dynamodb get-item --table-name LyraLearnTable --region "$AWS_REGION" \
  --key "{\"PK\":{\"S\":\"SONG#$SONG_ID\"},\"SK\":{\"S\":\"JOB#$JOB_ID\"}}" --output json
```
